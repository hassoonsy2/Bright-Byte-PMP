# Render Deployment Runbook

This runbook covers the Phase 4 deployment contract for Bright-Byte PMP on Render: managed resources, Cloudflare R2 attachments, SMTP delivery, browser origins, cookies, OAuth redirects, and verification.

## Render Topology

`render.yaml` defines the production topology:

- `bright-byte-postgres`: managed Render Postgres.
- `bright-byte-redis`: managed Render Key Value, used for Redis runtime state and the Celery broker.
- `bright-byte-api`: Django API web service. Its `preDeployCommand` runs migrations.
- `bright-byte-worker`: Celery worker.
- `bright-byte-beat`: single Celery beat scheduler.
- `bright-byte-live`: live collaboration/WebSocket service.
- `bright-byte-space`: Space SSR service.
- `bright-byte-web`: public web static site.
- `bright-byte-admin`: admin static site mounted at `/god-mode`.

Use paid Render Postgres and paid Render Key Value. Keep Render Key Value on `noeviction` when it backs Celery queues.

## Render Resources

Set these resource-backed values from the blueprint:

- `DATABASE_URL`: Render Postgres internal connection string.
- `REDIS_URL`: Render Key Value internal Redis URL.
- `CELERY_BROKER_URL`: Render Key Value internal Redis URL.
- `SECRET_KEY`: generated by Render and stable after creation.
- `LIVE_SERVER_SECRET_KEY`: generated on the API service and synced to workers/live.

Do not commit real credentials. Dashboard-only secrets belong in Render environment variables or secret files.

## Cloudflare R2

Create a Cloudflare R2 bucket for attachments. Use a bucket-scoped R2 API token with object read/write permissions.

Backend env:

- `USE_MINIO=0`
- `AWS_REGION=auto`
- `AWS_S3_ENDPOINT_URL=https://<account_id>.r2.cloudflarestorage.com`
- `AWS_S3_BUCKET_NAME=<bucket_name>`
- `AWS_ACCESS_KEY_ID=<r2_access_key_id>`
- `AWS_SECRET_ACCESS_KEY=<r2_secret_access_key>`
- `SIGNED_URL_EXPIRATION=3600`

Bucket CORS must allow the deployed browser origins that upload or download attachments. Include the web, admin, and Space HTTPS origins. Allow methods `GET`, `PUT`, and `HEAD`. Allow `Content-Type` and any provider-required checksum/cache headers the browser sends.

Manual verification:

1. Sign in to the deployed web app.
2. Upload an attachment from the browser.
3. Confirm the presigned `PUT` succeeds.
4. Download or preview the attachment and confirm the presigned `GET` succeeds.
5. Confirm the object exists in the R2 bucket.

## SMTP

Use an authenticated transactional SMTP provider. Configure either STARTTLS or SSL, not both.

Backend env:

- `EMAIL_HOST=<smtp_host>`
- `EMAIL_HOST_USER=<smtp_username>`
- `EMAIL_HOST_PASSWORD=<smtp_password>`
- `EMAIL_PORT=587`
- `EMAIL_USE_TLS=1`
- `EMAIL_USE_SSL=0`
- `EMAIL_FROM="Bright-Byte PMP <noreply@your-domain.example>"`

If the provider requires implicit TLS on port 465, use `EMAIL_PORT=465`, `EMAIL_USE_TLS=0`, and `EMAIL_USE_SSL=1`.

Manual verification from the API service shell:

```bash
python manage.py test_email <recipient@example.com>
```

Then verify an invite or magic-link email reaches a real inbox.

## Origins, Cookies, And OAuth

Choose final HTTPS origins before the first production build. Static site `VITE_*` values are baked at build time, so changing them later requires rebuilding web/admin/space.

Recommended first-deploy matrix:

| Service | Runtime env                                                                          | Frontend build env                                                                             |
| ------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| API     | `WEB_URL=https://bright-byte-api.onrender.com`                                       | `VITE_API_BASE_URL=https://bright-byte-api.onrender.com`, `VITE_API_BASE_PATH=/api`            |
| Web     | `APP_BASE_URL=https://bright-byte-web.onrender.com`, `APP_BASE_PATH=`                | `VITE_WEB_BASE_URL=https://bright-byte-web.onrender.com`, `VITE_WEB_BASE_PATH=/`               |
| Admin   | `ADMIN_BASE_URL=https://bright-byte-admin.onrender.com`, `ADMIN_BASE_PATH=/god-mode` | `VITE_ADMIN_BASE_URL=https://bright-byte-admin.onrender.com`, `VITE_ADMIN_BASE_PATH=/god-mode` |
| Space   | `SPACE_BASE_URL=https://bright-byte-space.onrender.com`, `SPACE_BASE_PATH=/spaces`   | `VITE_SPACE_BASE_URL=https://bright-byte-space.onrender.com`, `VITE_SPACE_BASE_PATH=/spaces`   |
| Live    | `LIVE_BASE_URL=https://bright-byte-live.onrender.com`, `LIVE_BASE_PATH=/live`        | `VITE_LIVE_BASE_URL=https://bright-byte-live.onrender.com`, `VITE_LIVE_BASE_PATH=/live`        |

Set backend CORS and CSRF from the same origin matrix:

- `CORS_ALLOWED_ORIGINS=https://bright-byte-web.onrender.com,https://bright-byte-admin.onrender.com,https://bright-byte-space.onrender.com`
- `CSRF_TRUSTED_ORIGINS=https://bright-byte-web.onrender.com,https://bright-byte-admin.onrender.com,https://bright-byte-space.onrender.com`
- `COOKIE_DOMAIN=` for Render-generated domains.

Leave `COOKIE_DOMAIN` unset for distinct Render `onrender.com` service URLs. Set it only after custom subdomains share a parent domain and auth is verified.

If OAuth is enabled, update each provider dashboard with callback URLs based on the final API origin. Rebuild static sites after any `VITE_*` origin change.

## Live Service

`bright-byte-live` needs:

- `API_BASE_URL`: API origin.
- `WEB_BASE_URL`: web origin.
- `LIVE_BASE_URL`: live origin.
- `LIVE_BASE_PATH=/live`
- `CORS_ALLOWED_ORIGINS`: comma-separated browser origins.
- `REDIS_URL`: Render Key Value URL.
- `LIVE_SERVER_SECRET_KEY`: synced from the API service.

Verify `https://<live-origin>/live/health` and a browser WebSocket/collaboration session after deploy.

## Deploy Order

1. Create or sync the Render blueprint.
2. Confirm paid Postgres and Key Value resources are created in the intended region.
3. Add dashboard-only R2 and SMTP secrets.
4. Confirm origin, CORS, CSRF, cookie, OAuth, and `VITE_*` values.
5. Deploy API first so migrations run.
6. Deploy worker, beat, live, space, web, and admin.
7. Rebuild static sites after any `VITE_*` value changes.

## Verification Checklist

- Render services are healthy.
- API migrations completed before serving traffic.
- Exactly one `bright-byte-beat` instance is running.
- Worker processes a queued job.
- `python manage.py test_email <recipient@example.com>` sends successfully.
- Browser attachment upload/download works through Cloudflare R2.
- API calls from web/admin/space are not blocked by CORS or CSRF.
- Sign-in persists across the chosen origins.
- Admin loads under `/god-mode`.
- Space loads under `/spaces`.
- Live health and WebSocket behavior work under `/live`.
