  <decision>Telemetry disable strategy: change Instance.is_telemetry_enabled default to False (requires Django migration) vs. env-var-only disable (OTLP_ENDPOINT="" in render.yaml)</decision>
  <context>
    Research recommends both layers (model default=False + OTLP_ENDPOINT="" in render.yaml). The model default requires a Django migration (safe: one BooleanField default change, no data loss). The env-var approach alone means that any existing instance row where is_telemetry_enabled=True (set by the model default at instance registration time) will still have telemetry enabled until the admin manually disables it via the admin UI.

    Two options:

    Option A (RECOMMENDED — research default): Change default=True → default=False in Instance model + generate migration + add OTLP_ENDPOINT="" to render.yaml. New deployments boot with telemetry off. Existing rows: either leave them (admin toggles off in UI) or add a data migration to set is_telemetry_enabled=False for all existing Instance rows.

    Option B (env-var only): Keep model default=True unchanged. Add OTLP_ENDPOINT="" to render.yaml only. Telemetry push task will fail gracefully on empty endpoint (caught by Exception handler in telemetry_metrics.py). No migration needed. Admin UI still shows "enabled" even though telemetry cannot reach its target.

  </context>
  <options>
    <option id="option-a-schema-migration">
      <name>Change model default + Django migration + render.yaml env var (recommended)</name>
      <pros>Correct state: is_telemetry_enabled=False in DB matches the intent. Admin UI reflects real state. Future deployments inherit correct default.</pros>
      <cons>Requires running makemigrations and applying migration at deploy time. Existing rows stay True until admin toggles or data migration runs.</cons>
    </option>
    <option id="option-b-env-only">
      <name>env-var only (OTLP_ENDPOINT="" in render.yaml)</name>
      <pros>No migration needed. Simpler.</pros>
      <cons>Model default stays True — admin UI shows telemetry "enabled" even though the endpoint is null. Misleading state. If OTLP_ENDPOINT is ever removed from render.yaml, telemetry resumes.</cons>
    </option>
