<objective>
Create the AGPL §13 network source-availability offer: a top-level NOTICE attribution file and a /source HTTP endpoint in the Django app that provides a machine- and human-readable link to the corresponding source code.

Purpose: AGPL §13 requires operators of network-served modified AGPL software to offer users a way to obtain the corresponding source. Without a /source endpoint and NOTICE file, serving real client data would be an AGPL violation. The NOTICE file also records Bright-Byte's attribution of the original Plane CE codebase.
Output: NOTICE file at repo root; source_disclosure view in web/views.py; path("source", ...) in web/urls.py; contract test; a checkpoint for the real source repo URL.
</objective>

  <decision>AGPL §13 source URL: what public URL should the /source endpoint and NOTICE file point to as the "corresponding source" for this deployment?</decision>
  <context>
    AGPL §13 requires the source offer to point to the "corresponding source" — i.e., the version of the code actually being served, including Bright-Byte's modifications (rebrand, de-monetization, security hardening). The upstream makeplane/plane repo is the BASE but does not include Bright-Byte's changes.

    Two options:

    Option A (RECOMMENDED for full compliance): Bright-Byte publishes its modified fork as a public repo (e.g., github.com/bright-byte/bright-byte-pmp) and /source points to that fork. This is the most legally robust interpretation — the corresponding source is the modified version.

    Option B (Practical fallback): /source points to the upstream makeplane/plane repo with a note that Bright-Byte's modifications are described in the NOTICE file. This is simpler to set up immediately but may not satisfy the strict "corresponding source" reading if Bright-Byte's changes are substantial.

    The code structure (SOURCE_AVAILABILITY_URL env var in render.yaml, /source endpoint) is the same regardless of which option is chosen — only the URL value changes.

  </context>
  <options>
    <option id="option-a-public-fork">
      <name>Publish Bright-Byte's fork publicly and point /source at it</name>
      <pros>Full AGPL §13 compliance — corresponding source is the actual modified version</pros>
      <cons>Requires creating and maintaining a public GitHub fork before serving clients</cons>
    </option>
    <option id="option-b-upstream-fallback">
      <name>Point /source at upstream makeplane/plane with modification notice</name>
      <pros>No new repo to set up; can be deployed immediately</pros>
      <cons>Legally weaker — corresponding source does not include Bright-Byte's modifications; Bright-Byte should still publish its fork eventually</cons>
    </option>
  </options>
  <resume-signal>Select: option-a-public-fork (provide the public fork URL, e.g. https://github.com/your-org/bright-byte-pmp) or option-b-upstream-fallback. The SOURCE_AVAILABILITY_URL env var in render.yaml will be updated to the chosen URL in Plan 03 Task 3 (or now if Plan 03 has not yet been executed).</resume-signal>
